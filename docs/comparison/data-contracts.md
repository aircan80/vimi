# Build comparison: data contracts and WoW semantics

Design proposal for #117. No comparison implementation is included. This review describes the APIs at `e0bbdb2`; an existing browser is not evidence that its inventory is exhaustive or its semantic projection supports every expansion.

## Comparison identity and reproducibility

A comparison is an ordered pair of frozen inputs, A → B, plus an explicit comparison-policy revision. Pin each side independently:

- Product ID and `BuildTypes.BuildRef` (build-config key, CDN-config key, region), displayed version/build label, root/encoding identities, and requested locale. BuildRef does not itself contain the human-readable version. A version string alone is not an immutable identity.
- Source table FileDataID, content key, observed layout hash, selected definition revision/schema match, parser/projection revisions, and row coverage. Include copy-row identity and reference dependencies when they affect the projection.
- Listfile snapshot, TACT-key fingerprint, and external-provider preparation snapshot/revision, flavor/product/build/locale, enabled-source and mapping policy. A process-local `DataSourcesService.revision()` is an invalid persistent source identity.
- Locale equality is the default. Different locales require explicit opt-in and a localization comparison label. Do not silently compare localized strings as gameplay changes.

Default comparison should stay within one product/branch lineage. Numeric IDs are namespace-local; cross-product/Classic-versus-Retail matching is an explicit experimental mode, never name-based automatic equivalence. Equal IDs are candidates for correspondence, not proof that two historical records represent the same game concept. A table identity combines its logical name and resolved FileDataID; differing IDs or layouts require a verified mapping before semantic comparison.

Freeze inputs before work starts. Daily source refresh must not mutate an in-progress comparison; offer a separate new run against updated sources. Record timestamps as observations, not gameplay-version authority.

## What constitutes a change

Represent entity presence, individual field values, coverage, and supporting evidence separately. Suggested field states are VALUE, KNOWN_EMPTY, UNKNOWN, PROTECTED, UNSUPPORTED, INVALID, and NOT_APPLICABLE. Null must not become empty string, zero, false, or an empty relationship set. NPC/Quest catalogs already distinguish null from known empty text.

Suggested result categories:

| Category | Required evidence |
| --- | --- |
| Observed on both, equal | Comparable supported fields have equal canonical values; identify fields that remain unassessed. |
| Observed field changed | Both field values are known under compatible semantics; preserve raw values and provenance. |
| Added / removed in assessed scope | Present on one side and authoritative absence in the same scope on the other. |
| Observed only on A / B | Absence cannot be established; do not inflate added/removed totals. |
| Availability changed | Encryption keys, downloaded state, missing dependencies, partial sections, limits, or failed preparation changed what could be read. |
| Interpretation changed | Same source bytes produce different meaning because schema selection, parser, formula, or projection changed. |
| External evidence changed | Provider revision, source selection, mapping, or precedence changed. |

Categories can coexist. A changed content key establishes different source bytes, not a particular semantic change. An unchanged content key establishes equal decoded-file identity, not equal provider labels or rendering. Changed EKey with unchanged CKey is an encoding/storage change, not automatically a game-content change. Different content/layout with equal supported projected fields means those assessed fields are equal; it does not mean the complete record or asset is unchanged.

For tables, `TableTypes.Entry` exposes READY/PARTIAL and `Counts` (declared/readable/excluded counts, format/layout); `get` exposes FOUND/ABSENT/PROTECTED/UNKNOWN. Consume readable PARTIAL rows. A partial scan cannot prove global absence; an exact lookup may prove an individual absence only when its underlying API guarantees it and the source evidence is retained. Fully drain stable-identity pages without filters, limits, cancellation, STALE, or errors before claiming exhaustive scope. READY alone does not certify that a concept's joins or bounded projection are complete. Missing tables/dependencies are not empty tables. Known-table inventory preparation completion means assessed outcomes, not universal readability.

Canonicalization preserves types, unsigned IDs, explicit array slots, effect/rank order, meaningful whitespace, nulls, and locale. Compare numbers by their schema semantics; do not round away differences or invent a universal float tolerance. Preserve raw text and separately compare display text. DB2 row ordinals, file-list positions, rendered pixels, diagnostic messages, observation timestamps, and paging cursors are not entity identities.

## Area contracts and current limits

| Area | Stable scoped identity | Initial comparable facts / boundaries |
| --- | --- | --- |
| Files | FileDataID within build lineage and locale/content variant | `BuildFiles.listMetadata` gives path/source, decoded size when known, CKey, format/source, storage, encrypted flag. Compare CKey and size independently of names and local presence. Root membership is distinct from encoded/download availability. A listfile rename is external naming evidence. Metadata enumeration must not call content-inspecting `list`, sniff files, or silently download everything. Root variant flags are not all exposed by BuildFile; use a reviewed lower-layer adapter if comparison includes every variant instead of the chosen locale. |
| Tables | Resolved table identity + DB2 row ID; individual field's verified semantic identity | `BuildTables` supplies inventories, schema, stable page identity, exact rows and copy records. Compare raw rows and schema separately. Copy aliases are distinct row IDs with source-copy provenance, not deletions or duplicate collapses. Reordered/renamed columns, changed arrays, reference targets, signedness, or layout cannot be matched by column ordinal alone. Report unmatched fields as schema differences. |
| Items | Item ID; relationship records retain their own IDs/slots | `BuildItems`/ItemDetail join Item and ItemSparse, names/icons, classifications, `ItemFactSet`, appearances and raw sources. Compare facts by key with state/agreement and `ItemFactValue` table/row/column evidence. ItemSummary exposes separate sparse/item keys and row outcomes: one readable half does not certify the other. Compare recorded allocation/scaling inputs as inputs; do not call them effective character stats. Item effects are separate bridge/effect facts, not concatenated tooltip text. |
| Creatures | Creature row ID; display slot ordinal and target DisplayID | `CreatureTypes` exposes name, raw facts, copy source, display slot/probability, classification, display/model chain and texture references. These are client Creature records, not the full server NPC population. Display slot ID, CreatureDisplayInfo.ID, CreatureModelData.ID and M2 FileDataID are different namespaces. Compare declared references before optional asset loading; a failed preview is availability, not a removed creature. |
| NPCs | NPC ID within compatible product/flavor; provider+snapshot+NPC ID for observations | `NpcCatalog` unions Blizzard/Questie/Polestar/EG Link and returns name, subname, levels and all evidence. Current Source contains provider/version/product/build/locale, but Snapshot has free-form diagnostics rather than typed completeness. Extend comparison adapters with explicit per-provider coverage; do not parse diagnostics to prove removal. Freeze precedence (currently provider enum order, first non-null field) and report winner changes separately from source values. A source disappearing cannot mean NPC removal. |
| Quests | Quest ID within compatible product/flavor; provider+snapshot+quest ID for observations | `QuestCatalog` currently supplies title, required level, quest level and evidence. It is not a complete quest narrative/reward/objective contract. Same typed-coverage gap as NPCs. Pickup/location facts use `LocationsService` independently; never infer starter changes from objectives, finishers, sourceItemId, or item drops. |
| Talents | Class ID, tree/tab ID, Talent ID; rank index and prerequisite edges | Classic `TalentTypes`: recorded row/column, ordered rank spells, prerequisite talent/rank index, name/description/icon, tree order/background. Compare talent moves independently of spell changes; prerequisite rank is zero-based. Localized names and resolved description are derived from additional spell tables. Missing rank spell rows must not erase existing talent identity. Retail's modern tree/node system is not covered by this Classic contract. |
| Races | Race ID; class ID; racial ability record/spell ID; ChrModelID+sex for variants | `RaceTypes` exposes name/order, lore/faction, recorded class links and racial ability facts. `RaceMediaTypes.Variant` supplies display/model/M2 references. Compare declared links without guessing current account unlocks or character eligibility. Appearance/customization, selected starting loadout, geosets, texture assets and voice clips are separate evidence layers. Current textured preview is narrowly reviewed; neutral/unsupported rendering is not a changed appearance. Pixel comparison is not an initial semantic contract. |
| Dungeons | Map ID for instance; difficulty/queue/encounter/area record IDs within their own tables | `DungeonTypes`: name/kind/maxPlayers/area/expansion; difficulty IDs/labels/caps/messages; queue difficulty/tuning/min/max; encounter order/display/icon and sourced descriptions. Do not match encounters by display ID or infer missing bosses, loot, entrances, lockouts, or difficulty support from absent optional sources. Catalog/detail states are aggregate: preserve per-table Entry evidence and assessed relation scope. |
| Mounts | Mount.ID; MountXDisplay record ID for variant edges | `MountTypes` provides localized name/description/sourceText, sourceSpell/sourceType/mountType/condition/flags and display variants with condition/source table. Compare reference changes separately from model asset bytes. Condition IDs/flags are recorded facts, not eligibility, ownership, speed, or a guarantee an appearance is usable. The catalog's PARTIAL/READY is insufficient to prove every optional display/condition source complete. |
| Professions/Recipes | SkillLine.ID, category ID, SkillLineAbility.ID; result/effect identity requires raw source row and effect index | `ProfessionTypes` supplies category/profession names/descriptions, ability spell/name/icon/minimumRank/category, raw threshold/acquire/class/race masks, ordered reagent slots and tools, result kind/item/enchantment/recorded amount/quantity and sources. Do not key recipe rows only by spell ID: multiple skill-line ability rows can share it. Preserve reagent count unknown versus zero. Results currently lack a dedicated effect index field; adapter must recover explicit source identity or compare an evidence-preserving multiset, never zip lists by position. Quantity stays unknown when current source semantics cannot prove it; no blanket base-points+1. Thresholds are not simulated skill-color/player state, and acquisition method is not a specific trainer/drop NPC. Exact Forever projection first; other layouts can be unsupported even though raw-table comparison works. |
| World | Map.ID, AreaTable.ID; terrain tile (MapID,x,y) and layer/asset roles | `WorldService` exposes map name/directory/type/WDT and area hierarchy/map, WDT tile inventory, lazy terrain. Compare map/area records and WDT membership first. WorldFormats has tile x/y/root/mapTexture/minimap IDs; raw ADT asset changes are file facts. It does not provide a complete semantic diff of terrain height, placements, liquids, WMO interiors, or doodad instances. Global-model worlds and unreadable tile manifests require explicit states. |
| Spells (supporting facts) | Spell ID; related table record IDs/effect index | There is no complete standalone spell browser/catalog comparison contract. `SpellTexts` supports bounded lazy raw/display description and substitution evidence; item effects/talents/races/professions consume subsets. Compare referenced spell source rows and raw descriptions first, with rendered text/substitution status separately. Unresolved `$s1` becoming resolved after parser/key updates is not automatically a Blizzard change. Do not promise all-spell gameplay diffs. |

### Locations and artwork are distinct comparison dimensions

`LocationTypes` preserves provider provenance and source coordinate spaces. Questie AreaID percentages, Polestar MapID world coordinates, and EG Link UiMap normalized coordinates must not be compared as interchangeable numbers. Questie's third scalar is phase, not z. EG positions are player observations, not guaranteed NPC spawn points. Compare pickup entity kind+ID, native-space facts, and snapshot first. A changed map assignment/projection or artwork can move a marker without an external source location changing. Never equate AreaID, MapID and UiMapID. `LocationMapsService` phase-0 artwork and UiMapAssignment mapping have their own table/asset dependency identities; unavailable or ambiguous mappings remain unknown.

## Proposed comparison-layer boundary

Add a concepts-level comparison component after review, borrowing public build/files/tables/concept interfaces through application-owned leases. It returns immutable paged DTOs and typed coverage/evidence; GUI issues commands and renders them, with no SQL, DB2 parsing, direct provider-repository access, or CDN downloads of its own. Existing catalog snapshots without typed coverage need adapters before authoritative presence deltas can be offered. Avoid making every concept DTO depend on comparison types.

A minimal proposed snapshot consists of: immutable side identity; area and policy version; source dependency manifest; identity key; fields each with typed state/value/evidence; relation-set coverage; enumeration progress/completion. Persist result pages and dependency manifests, not open workspace handles, mutable JavaFX state, or exception strings as control data. Give summaries observed/equal/changed/observed-only/confirmed-added/confirmed-removed/unassessed counts with denominator/scope; do not combine unknowns into unchanged totals.

Use stable ID-ordered bounded merge joins or sorted persisted manifests, cancellation between pages, background priority, bounded queues, and backpressure. File enumeration can be millions of rows; do not create two full GUI lists or eagerly render/decode all models. Concept detail, models, audio, map tiles and file payload diffs are lazy follow-ups. Suggested initial budgets are configurable batch sizes, result-page sizes, persisted-byte limits, and maximum concurrent source reads; validate actual budgets before implementation. Resume only from a committed manifest/checkpoint with identical dependency identities; a canceled or quota-limited prefix remains explicitly incomplete.

## Persistence, accounting, and lifetime

Keep the unified SQLite catalog and existing pack payload store. Use `GeneratedStore` for immutable comparison manifests/pages (new versioned key domain containing ordered A/B and all policy/source identities). GeneratedKey is a caller-chosen 16-byte identity; it does not automatically account for builds, locales or algorithms. Do not introduce a second blob database or GUI SQL path.

Retain original file/table source publications under the appropriate build's existing ownership boundary. Reused bytes stay deduplicated; reading shared CKeys/EKeys does not create a private copy. A comparison artifact depends on both builds: proposed ownership must explicitly attach the same derived object to both build owners through a reviewed catalog/publication API, or retain a distinct comparison owner with explicit dependency leases. Do not assume raw `GeneratedStore.put` attaches two builds: GeneratedStore explicitly knows nothing about builds. Decide this ownership policy before implementation, including whether deleting a comparison releases only its derived results and whether forgetting one build invalidates the comparison.

Do not mix comparison artifact size, build inventory size, decoded file size, encoded downloaded bytes, or SQLite metadata overhead. Existing `StorageAccounting`/unified library reporting owns these definitions; no second sum of display rows. Build unique/shared original/derived figures remain library-relative (all retained owners), not automatically A-versus-B. A pairwise report needs a separate explicitly scoped catalog query for A∩B/A−B/B−A, using distinct physical object keys/lengths and role, never double-counting references. Sharing can change when another build is retained; pin observation/revision for reproducible accounting. These live storage figures are not gameplay changes.

Two comparison sessions must coexist without stealing or closing an unrelated browsed build's handles. Normal application navigation still follows the user's close-on-leave policy. Native workspace ownership currently belongs to composition; introduce explicit comparison leases/ref-counting or dedicated comparison sessions, not a second call that steals the active workspace. Cancellation must drain comparison workers, then release borrowed concept services, tables, files and build handles in dependency order. Closing a comparison must not close the browsed build or shared provider repositories. Freeze prepared-provider snapshot handles for the run; refresh can publish a new snapshot without deleting data needed by active leases. Confirm this retention capability instead of assuming current per-view handles provide it.

## Phased scope and validation gates

1. **Inventory MVP:** ordered build/locale pair; metadata-only files and table/schema inventory; CKey differences; coverage/availability distinctions; bounded session-local pages/restart; durable resume remains deferred. Confirm API identity and exhaustive-scope guarantees before showing added/removed.
2. **Raw table rows:** ID merge, schema-aware comparable fields, copy rows, exact absence, provenance and dependency manifests. Test encrypted/excluded sections, new keys with identical files, stale pages, limits, cancellation and definition upgrades with unchanged bytes.
3. **Selected supported concepts:** Items first, then Classic talents and other reviewed projections. Every area above is a candidate, not a claim of implemented support. Separate an entity change from changes to shared referenced spells/assets. Golden offline fixtures should cover same spell reused by two recipes, unsupported layouts, unknown-to-known fields, and partial joins.
4. **External evidence:** frozen provider snapshots and source-specific changes, then merged NPC/quest display-winner changes. Test disabled/failed sources, source precedence, equivalent numeric IDs in incompatible products, known-empty titles, and unchanged Blizzard data with refreshed providers.
5. **Assets/world detail:** optional byte/format/model/terrain inspection behind lazy bounded jobs, with reviewed semantic contracts. Pairwise storage reports are independently labeled and tested for multi-build deduplication/deletion.

Outstanding decisions for architect/independent review: persistent source retention/leases; typed completeness adapters; authoritative locale/root membership inventory; schema-crosswalk admission; result ownership/deletion; supported pair lineage; artifact quotas/resume policy. None require speculative production changes during this design task.
