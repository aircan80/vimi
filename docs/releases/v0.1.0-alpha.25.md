# VibeMiner v0.1.0-alpha.25

World Explorer now draws outdoor buildings. Around the camera, the exteriors of
WMO buildings placed on each terrain tile are drawn in the same view and depth
as the terrain. This is on by default; `-Dvimi.world.exteriors=false` turns it
off. Terrain always loads first: buildings are prepared only once every nearby
tile's terrain is ready, nearest tile first, and are attached to a tile after
its terrain is shown. If the camera moves to unloaded terrain, building work
stops so that terrain can load. The status line shows "loading buildings", how
many buildings are drawn on how many tiles, and on how many tiles they failed.
A failure costs only that tile's buildings, never its terrain. Drawing is
BASIC: only exterior groups and opaque materials, with their first texture and
the existing fixed light and fog, not the client's lighting. Doodads, cutout
and blended materials such as glass, vertex colours and liquids are not drawn,
interiors are not entered, and each tile is capped at 64 buildings. What is
left out is not yet counted in the window. On one warm local cache, terrain for
seven Azeroth tiles was ready in about 3.6 s with or without buildings, and
their 43 buildings were attached by about 8.5 s. A cold cache was not measured;
buildings arrive later there, and one slow fetch can briefly hold up terrain.
Only Linux Vulkan was tested; Metal and DirectX 11 were not run.

The dungeon interior view can list floors and map layers. A new Floors / map
layers (UiMap) list shows each UiMap that the build's UiMapAssignment table
assigns to a WMO group of the drawn model. A row links only when its group ID
matches exactly one recorded group and it names no WMO placement; nothing is
guessed from heights or near IDs. Floors are listed by UiMap ID, with a floor
nested under its parent when the parent is also listed, and each shows its
recorded type. Click a floor or press Enter to frame all of its groups. Rows
that do not link are counted by reason with example group IDs, for example
rows that name a WMO placement, which are not matched yet. The entrance is
still unknown. This has not been checked against real dungeon data, so how
many real floors link is not yet known.

World Explorer reports which creature model each NPC spawn would use. Nothing
is drawn yet. Using the opened build's creature tables, a spawn's model is
chosen only when its creature record declares exactly one display and that
display leads to a model file. Several declared displays are reported as
ambiguous, because the client picks one at random; missing or broken links are
reported as unresolved, with the reason. Click a spawn marker to see the
choice in the inspect footer: the model file ID, its listfile path ("name
unknown" without one), the display and model data IDs, and the source. It reads
"model: resolving…" while the lookup runs. The status line counts each outcome
over the drawn markers. Lookups run in the background, nearest markers first.
It has not yet been checked how many spawns qualify on real data.

The Races voice panel now says where each clip comes from and why others are
missing. The selected clip shows its source chain, from the EmotesText row
through EmotesTextSound, SoundKit and SoundKitEntry to the file ID. A "Not
playable" list names refused links and the reason: an emote not recorded in
the build, no SoundKit, a SoundKit with no entries, an entry with no valid
file, or an ambiguous link, where the race, sex and class rows for one action
name more than one SoundKit. Ambiguous links are refused rather than guessed,
because the client's runtime choice is not evaluated. Up to 32 refusals are
kept and six are shown; notes below the list give the rest of the picture.
Clips still play only when you press Play.

Race models still have no idle animation, but the preview now says why. In
place of the animation toggle it reads "Idle animation unavailable" with every
reason: the model uses a separate skeleton file, it uses external bone files,
its Stand animation is refused, or Stand playback is not yet implemented for
race previews. Model source details list the Stand facts and, for bone files,
how many were validated, refused or unreadable and how many bone matrices they
hold. Vimi now reads these bone files strictly. On one Forever 1.60.1 build,
every bone file it found was well formed, but how the client applies them is
not yet reviewed, so no race model plays an animation.
