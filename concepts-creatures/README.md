# Creature concepts (layer 6)

`CreaturesService` joins layer 5 `Tables`, `BuildModels` and `BlpImages` for one build and locale. `Creatures` opens a `BuildCreatures` handle; listing returns primary-name matches in table row order, while `get` follows four declared display slots and preserves every resolved prefix and lower-layer failure. `MemoryCreatures` is the independent seeded test fixture for consumers of this boundary.

## Implemented reference scope

This ports all four pinned C# `VibeMiner.Concepts/Creatures` production sources, using reference commit `4fd92d2` (the later audited `1d6632e` has identical Concepts sources/contracts):

- The sixteen-field Creature profile checks selected DBD names, kinds, integer widths/signs and array cardinalities. Source text, copy provenance, invalid/empty/whitespace primary names, classification labels, display probabilities and negative/zero display references remain distinct.
- Literal primary-name queries use the common `ConceptQueries` .NET ordinal-ignore-case policy, limits 1–50, bounded scans and opaque query/build/locale/page-size/identity-bound cursors. Exact lookups preserve absent, unknown and protected outcomes. Unreadable, stale, unsupported-schema and invalid-source outcomes are explicit.
- Reviewed CreatureDisplayInfo and CreatureModelData layouts qualify only verified scalar ModelID/FileDataID edges. Details retain table entries, raw rows, reviewed facts, remaining raw cells, all four variation slots and protected keys. An absent record in a partial table remains unknown.
- Model and main-SKIN reads use layer 5. Declared textures, model dependencies (including skeleton, particle, animation, texture and bone references) remain accessible through the model's layer 5 reference evidence; no dependency bytes are invented. Opaque/alpha-key batches determine drawn textures; blended surfaces are counted. TXID and types 11–13 use their exact source identities. Only drawn resolved textures receive BLP header inspection. Typed model, skin and image failures retain lower-layer codes, observations and keys.
- Files open lazily, listing never follows display/model chains, and repeated display/model/texture reads coalesce within one detail. Handles reject new operations after close and drain accepted work before closing files and tables, including when an outward future was canceled.

The Java port completes backend correctness gaps in the C# implementation: detail-scoped row coalescing now satisfies the existing reference comment, accepted operations retain their resources through close, canceled opening futures dispose late handles, and `CreatureModel.references` exposes every actual typed layer 5 dependency rather than only texture references. Deterministic tests cover these behaviors. Virtual work admits at most 512 concurrent operations process-wide and refuses excess work immediately with `CREATURES_OPERATION_LIMIT`; no admission thread waits for a permit.

## Explicit scope boundaries

As in the pinned reference, character-model baked textures, unsupported materials/geometries and unresolved non-creature texture bindings are explicit refusals, not guessed game facts. This module describes static appearance readiness; it does not draw HD models, animate, pose, bake character skins, resolve item/emblem bindings, or implement GUI rendering. No known pinned Creatures production method remains unported. Live client-build certification and renderer work are separate from the authored deterministic backend checks.

## Checks

Requires JDK 25 and the repository's pinned Gradle wrapper:

```sh
./gradlew :concepts-creatures:check :concepts-creatures:assemble
```

Unit tests run shared real/fake contracts, projection failures, partial/protected chains, lazy/coalesced dependencies, close/cancel draining and native authored model/SKIN/BLP appearance paths. Checked-in TSV goldens were generated by the original C# Concepts assembly; the ordinary tests compare Java bindings, exact cursor bytes, classifications, finite Single round-trip values and eight skin/material profiles against those results. Authored asset bytes are reused directly from `formats-assets/src/test/resources/golden`, whose original-source regeneration is independently checked by that module.

To independently regenerate and compare creature goldens with the pinned reference checkout and .NET 10:

```sh
./gradlew :concepts-creatures:interopTest \
  -PreferenceRoot=/path/to/vibeminer \
  -Pdotnet=/path/to/dotnet
```

The harness uses a friend assembly named `VibeMiner.Concepts.Tests` and a project reference to the original `VibeMiner.Concepts.csproj`. It needs the reference backend sources and locked restore packages, plus the Java repository's existing authored asset fixtures. It never rewrites checked-in goldens. No test uses live network I/O or game credentials.

## Preparation and on-demand media

Concept handles expose `warmup(priority, token)` with immutable per-lookup results.
Preparation builds only reviewed, bounded table indexes and reports unsupported,
partial or resource-limited inputs explicitly. Retain the same warmed handles in
the application context; closing and reopening them discards in-memory indexes.
Warmup performs no icon/model/texture I/O and does not claim universal table readiness.

`getData(id, priority, token)` returns table facts and declared media identities
without opening asset files. Existing `get` preserves full-detail compatibility
and can be requested separately for asynchronous media enrichment. Item icons
use NOT_REQUESTED and models NOT_READ; creature model IDs remain in display chains
with no inspected model payload. Local queries still execute asynchronously.
